# Lifecycle Enforcement

Pi Forge's lifecycle extension observes normal parent-session Pi tool events.

## Enforced boundaries

- Direct `git commit` through the Bash tool is blocked. Commits must use the source-control skill and `commit-gate.sh`; the gate treats `dev`, `main`, and `master` as primary branches that require explicit authorization.
- From an attached existing ref, exact direct `git -c core.hooksPath= -c core.fsmonitor=false switch -c <fresh-non-primary-branch>` uses standing authorization at the same `HEAD`; task-owned staged and unstaged changes may remain because the operation does not change the checked-out tree. The parser rejects primary/existing/invalid branch names, alternate spellings, options, start points, repository selectors, and shell composition.
- From a clean attached checkout, exact direct `git -c core.hooksPath= -c core.fsmonitor=false worktree add -b <fresh-non-primary-branch> <absolute-nonexistent-path> HEAD` also uses standing authorization. The runtime requires a valid absent local branch and canonical absent target outside the current project root, beneath its parent or the OS temporary root, and outside common sensitive paths; it repeats target canonicalization and nonexistence after its asynchronous Git checks immediately before allowing the tool call. Relative/existing paths, symlink-resolved nested targets, other start points, `-B`, missing or changed neutralizers, other options, and worktree removal/move/prune/lock/unlock remain gated. The neutralizers disable checkout hooks and filesystem-monitor commands; worktree materialization can still invoke configured checkout filters, so this standing path is for trusted projects rather than untrusted candidate code.
- On an existing non-primary current branch with a clean index and worktree, one exact direct `git -c push.followTags=false -c push.gpgSign=false -c push.pushOption= -c push.recurseSubmodules=no -c push.useForceIfIncludes=false push [-u|--set-upstream] <remote> refs/heads/<branch>:refs/heads/<branch>` shape and one exact direct `gh pr create` shape with explicit `--repo owner/name`, base, current head, title, and bounded inline body use standing authorization without another prompt. The push parser requires every configuration neutralizer and rejects force, tags, deletion, signing, configured push options, recursive submodule pushes, atomic mode, extra refspecs, other options, and shell composition. The PR parser rejects omitted or mismatched repository/head, `--body-file`, empty or oversized body text, unsafe shell-expansion characters, extra options, shell composition, and every PR mutation other than create.
- Every existing-branch switch, other branch/worktree mutation, Git push or PR mutation outside those forms, destructive Git state change, recursive deletion, privilege escalation, and broad permission change requires one interactive confirmation for the exact tool call. The classifier grants read-only treatment only to a closed `git branch` display grammar; force/reset, upstream, abbreviated or unknown options, and positionals outside an explicit list mode remain mutating. Bare `git stash` and write-shaped `git config` forms are also mutating. Headless execution fails closed.
- Write and edit calls targeting common environment files, credential stores, Git hooks/configuration, credential-bearing user configuration, and the effective Pi agent configuration/consent directory require one interactive confirmation. Existing paths and their nearest existing parent are canonicalized through symlinks first.
- The protected implementation writer is accepted only as one direct launch with explicit `async: false`. `forceTopLevelAsync` blocks the launch, and repository async defaults cannot replace the explicit value. The writer has no supervisor or subagent tool, so it must finish or return a clarification request before the parent verifies.
- A successful observed source or build-input write/edit, or an actually launched protected writer, invalidates earlier verification. If no recognized successful check follows, `agent_end` queues one bounded follow-up asking for fresh verification or an explicit unchecked-risk statement.

Lifecycle state is persisted as `pi-forge.lifecycle.v1` custom entries. Those entries contain only monotonic counters and do not participate in model context. The verification follow-up is a visible custom message and does enter context because it must trigger the corrective turn.

## Evidence rules

Verification recognition is deliberately conservative. It accepts common test, lint, type, build, and validation commands, including safe `&&` chains. It rejects pipelines, semicolon chains, `||`, newlines, commands that merely quote tool names, failed results, and checks that ran before the last observed source mutation.

A custom project check may not be recognized. The follow-up fires once per mutation sequence; the agent can then run a recognized equivalent or state why the custom evidence applies and what remains unchecked.

## Limits

This extension is a workflow control, not a shell sandbox or complete command parser. The narrow branch/worktree preparation, push, and PR-create forms are syntactic allowlists plus adjacent state checks, not atomic state binding or proof of repository ownership, remote policy, CI success, or semantic payload safety. Git itself supplies the final fail-closed absent-branch/path checks, but a concurrent same-user actor remains outside the boundary. Obfuscated shell, aliases, custom tools, direct filesystem APIs inside a process, and project code can bypass tool-name and command-shape observation. Bash commands can mutate source without a write/edit event. Git aliases can hide subcommands. Interactive confirmation establishes intent for one visible call, not containment.

Package identity and capability enforcement for protected subagents remains in `extensions/agent-policy.ts`. OS-level isolation remains necessary for hostile execution.
